# metiche — hackathon submission

## Short version

*(for a form field with a length limit)*

**metiche** — Mexican slang for *nosy* — is an MCP server that every teammate's coding agent
connects to, so five agents stop quietly building the same thing five different ways.

The environment is the agent's own tool-call loop, and that is the whole idea. MCP cannot push, so
metiche does not notify agents; it makes findings **ride back inside the response to a call the
agent was already making**. An agent declares what it is about to touch, and the collision — a path
someone else already holds, a response shape that will not match, a team decision the plan
contradicts — comes back in that same response, before it has opened a file. A chatbot cannot do
this: it has no shared state across people, it is not present at the moment of decision, and it has
nothing to say to the other four agents in the room.

The server has no model and no API key. Path overlap and contract mismatches are decided
deterministically in SQL and Go; semantic questions are handed back to the *calling agent's own
model*, which answers with a verdict. The intelligence is already distributed across the team's
agents, so the server's job is shared memory and referee.

Go backend generated by nuzur, hand-written MCP server on the official `modelcontextprotocol/go-sdk`
over streamable HTTP, MySQL, and a templ + htmx + SSE board live at **metiche.xyz**. Apache-2.0,
public repo.

## Full version

### The problem

A small team — a hackathon team especially — collapses into a queue. Everyone ends up blocked on one
person, usually whoever owns the frontend, waiting to find out what they built and what shape it came
out in. Nothing lands in anyone else's world until it lands in git, and by then the cost of being
wrong is a merge conflict or forty minutes of a login screen wired to an endpoint nobody is building.

The work is parallelizable. The *awareness* is not.

Meanwhile every person on that team is running a coding agent that already knows, in plain language,
exactly what it is about to do — a second before it does it. That knowledge is sitting in five
separate terminals and nowhere else. metiche is the thing that collects it.

### The environment is the tool-call loop

metiche is an MCP server. That makes its environment neither a chat window nor a web app: it is the
inside of somebody else's agent loop, and the entire design falls out of one constraint of that
environment — **MCP has no push**. A server cannot interrupt an agent. It can only answer.

So metiche does not notify agents. It makes findings ride back inside the response to a call the
agent was already going to make. An agent calls `declare_intent` with a summary of what it is about
to do and the paths it is taking; detection runs synchronously inside that call; and the collision
comes back in that same response — before the agent has opened an editor, while changing course is
still a thirty-second decision rather than a rebase. Every response also carries a `pending` count
of instructions, conflicts and reviews, which is how anything asynchronous ever reaches an agent: a
person's nudge from the board is stored as an instruction and delivered on the target agent's next
call, and a bare 60-second `heartbeat` is enough to collect it.

That shape is why this cannot be a standalone chatbot. A chatbot has no shared state across five
people's machines, is not present at the instant a decision is made, and — the part that matters
most — has nothing to say to the *other* four agents. metiche's value is not that it answers well;
it is that it is the only thing in the room that can see all five agents at once and can speak into
each one's own loop at the moment that agent is deciding something.

The environment shapes the workflow down to the verbs. There is no user-facing "claim" verb, because
an agent will not reliably learn two concepts: `declare_intent(summary, paths, mode)` creates the
intent and its file claims in one transaction. Claims are advisory and expire, because an agent that
gets blocked by a tool learns to route around the tool. Responses are budgeted — a hard cap of ~700
tokens, typically ~90, with a documented cut order ending in "drop the block and let the agent fetch
it" — because a tool that floods the context window is a tool the model starts ignoring. And every
MCP annotation is explicit (`readOnly` / `idempotent` / `additive`), because the spec's
`destructiveHint` defaults to *true* when omitted, and an unannotated surface gets gated behind a
confirmation prompt on every call.

### The innovation: a coordination server with no model in it

metiche never calls an LLM and never needs an API key. This is a public repo, and requiring a model
provider credential to start the server would be a non-starter — that single constraint shaped the
whole detection design, and it turned out to be the better architecture anyway.

The mechanical collisions are decided deterministically, in SQL and Go:

- **Path overlap.** Patterns are normalized on insert, matched with real glob semantics via
  `bmatcuk/doublestar` (the standard library's `path.Match` has no `**`), and scored on a fixed
  severity matrix — read×read is never a conflict, identical exact path is critical, a rename against
  anything is high because renames break readers silently — then adjusted deterministically for same
  person, same branch, over-broad claims and hotspot paths.
- **Contract mismatch.** An agent publishes what it *produces* or *consumes*; the server canonicalizes
  each shape and hashes it server-side (agents never compute the hash, or two agents describing the
  same shape would produce different bytes and deduplication would evaporate). One distinct hash means
  everyone agrees and the check ends in a single count. Otherwise a directional comparison finds the
  four things that actually break a build, and *direction* decides which side is at fault.
- **Nobody is building it.** A `consumes` assertion with no active `produces` behind it — *"Beto is
  coding against an endpoint nobody is building"* — which at a hackathon is the highest-value signal
  in the system, and which falls out of the same tables as a query rather than a judgement call.

The semantic questions — *does this plan contradict a decision we recorded?*, *are these two agents
doing the same work?* — go back to the caller's own model. The server returns a small review block of
candidate decisions and similar intents, each stamped with a server-computed, revision-scoped
`pair_key`; the agent's model reads it and answers with `report_judgement`. A unique index assigns
each pair to exactly one agent, so N agents never burn N× tokens on the same question, and a judged
pair never returns unless one side materially changes.

That inverts the usual architecture. The intelligence is already distributed across the team's
agents; the server's job is to be the shared memory and the referee, not another LLM. It also means
metiche runs with no egress at all.

Noise control is treated as a feature rather than polish, because an agent that learns to ignore your
tool output is unrecoverable: generated code never enters the claim table (codegen writes most of the
Go here, so without that rule every agent would collide with every other agent on generated CRUD);
one human's two agents are de-escalated and never interrupt; a pair surfaces once forever unless it
escalates; the record floor and the notify floor are deliberately different; model verdicts interrupt
a person only above a confidence threshold, because a model asked "is this a conflict?" has a strong
yes-bias; and no conflict is ever surfaced without a suggested next action. *"You and Ana both hold
auth.go"* is noise. *"Ana holds auth.go (write, 4m, feat/auth); consider consuming her POST /api/login
contract instead"* is signal.

### Technical execution

**Backend.** Go 1.26. The data layer — 24 entities, sqlc-generated queries, the MySQL schema — is
generated by **nuzur** from a versioned schema, and the MCP server is hand-written in the `app/`
zone that survives regeneration. The tool surface is built on the official
**`modelcontextprotocol/go-sdk`** (v1.7.0) served over **streamable HTTP**, with `chi` for routing and
Uber's `fx`, `zap` and `config` for wiring.

**The write path is the interesting part.** Every event-producing call takes
`SELECT ... FOR UPDATE` on the team row — the team row *is* the sequence lock — appends to a
per-team append-only event log, and runs detection **inside that same transaction**. Check overlap
outside the lock and you get precisely the time-of-check/time-of-use race where two agents both see a
clean world and both insert. Nobody is ever blocked; ordering assigns *responsibility*, not
permission — the later declarer is told synchronously because it has the information in hand and
hasn't started yet. Calls are idempotent: the response is stored on the event and a retry with the
same key replays it verbatim instead of applying twice. A `metiche_team_lock_hold_ms` histogram ships
from day one with a documented p99 > 25ms tripwire, because the rule that protects the whole write
path — nothing inside the lock does I/O or loops over an unbounded row set — needs a number watching
it.

**Tested against reality.** The detection primitives are pure functions with table-driven tests
(path normalization, glob overlap, the severity matrix and adjusters, canonical bytes stable across
key order and whitespace, the four directional comparison branches, pair-key symmetry and revision
scoping). The write path is tested against a real MySQL with no sqlite fallback and no mocks, because
what is being proven is a property of InnoDB row locks and unique indexes: 24 goroutines writing at
once produce distinct sequences, a gapless log, no lost update on the team cursor, exactly one
project row despite 24 racing creates — and the lock-hold p99 measured 3ms against its 25ms tripwire in the
same test. Sixteen concurrent retries of one call produce one event and one answer.

**Frontend.** The board is a second Go service: **templ + htmx + server-sent events**, no JS
framework and no build step beyond `templ generate`. It consumes the backend's JSON SSE and
re-broadcasts **rendered HTML fragments**, so the browser does no templating. The two cursors map
onto two htmx behaviours on one stream: `sequence` appends to the timeline, `board_revision`
re-renders the board. Reconnection is exact — every frame carries `id: <sequence>`, the browser
replays it as `Last-Event-ID`, and the store drops anything it has already applied. Server-to-browser
delivery is an in-process fan-out on commit with a 250ms database tail as the cross-process backstop,
on one datastore: MySQL, no Redis, no message bus, with the capacity analysis and the tripwires for
when another layer would genuinely be needed written down rather than guessed at.

**Deployment.** One namespace on **microk8s** behind **ingress-nginx** with **cert-manager**: the
backend, the board, and MySQL 8 on a PVC, installed by Helm charts and a preflight script that prints
every assumption it makes about a box it did not build. SSE gets explicit `proxy-buffering: off` and
hour-long proxy timeouts, because nginx's defaults break a correct deployment in two independent ways
that both look like a frontend bug. Credentials are generated on the box into a root-owned file
outside the checkout, never passed as a command-line argument, never echoed — a public repo means
nothing in `deploy/` may ever become a secret. "No credentials" is not "no auth", either: joining
takes a team join code, which mints a per-agent bearer token server-side.

### The experience

For a person, joining is one command — `curl -fsSL https://metiche.xyz/install.sh | sh` — which
installs the `metiche-teamwork` skill and registers the MCP server with Claude Code, Cursor or
Windsurf, writing the join code to a mode-0600 file in the home directory and never into a
repository. After that there is nothing to operate. The agent learns the cadence from the skill, and
the server's own instructions tell any model that connects what the loop is.

For the team there is a board: a lane per person, their agents, each agent's current intent and
status line, the paths it holds and the conflicts it is in — plus an entanglement graph, a
produces/consumes matrix (an empty column in that matrix is a bottleneck you can see), decisions, and
run history. A person can raise a nudge — stop, steer, ask — and it reaches the target agent inside
its next tool call.

And the ratio that is actually the product: in the end-to-end scenario, agent A defines the login
endpoint, agent B collides on `auth.go` and is told in its own tool response, B's model checks its
plan against the recorded cookie decision, B's consumer contract mismatches A's producer, and A finds
out on its next heartbeat, never having polled. Count the interruptions to A: **one**, and it was
actionable.

### Honest status

The board is **live and deployed** at metiche.xyz, rendering from recorded fixture streams over the
real SSE mechanism, with the seam for the live backend behind a single flag.

Built and tested: the detection core (paths, contracts, pair keys — all green), the MCP core write
path (team lock, append-only event log, idempotent replay, response envelope, panic-safe tool
wrapper, auth and rate limiting), seven of the fifteen tools registered on the real SDK server
(`create_team`, `join_team`, `start_session`, `end_session`, `heartbeat`, `get_team_state`,
`health`), the SSE hub and web API, and the deployment.

Not finished: tools 5–14 — `declare_intent`, `update_intent`, `check_paths`, `publish_contract`,
`record_decision`, `get_review_context`, `report_judgement`, `resolve_conflict`, `get_instructions`,
`report_back` — register at a documented seam in the tool surface, wiring the tested detection
functions onto the tested write path. Until they land, the full end-to-end loop is not closed. This
is not a working hosted product yet, and it would be worth less to say otherwise: the plan for every
remaining piece is in [`PLAN.md`](PLAN.md), which is the spec the rest of this describes.

Apache-2.0 — permissive on purpose, because a coordination tool only works when *everyone* on the
team installs it, and a licence review is exactly the kind of queue metiche exists to remove.
