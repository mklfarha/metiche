# metiche — learnings

What went wrong (or nearly did) while building and running metiche, why, and the rule we
follow now. Dates are 2026-09-12/13 (UTC evening/night). Entries marked **open** are not
fixed yet.

Each entry: **what happened** → **why** → **rule** → **enforced by**.

---

## 1. Identity is never invented by the model

The single root cause behind the failed demo and the missed collision afterwards: an
identity value was left for an LLM to choose.

### 1.1 `client_key` (the demo)
- **What happened:** two agents on one laptop. The bearer named the *person*, so the server
  needed a `client_key` to tell agents apart. An agent cannot learn its own key (chosen by
  the installer, stored nowhere it can read). One agent guessed four times; the other
  refused. The installer default was per *machine*, so two clients collapsed into one agent.
- **Rule:** the token names the agent. One join per client; `client_key =
  <machine_id>-<client>` is generated by the installer, never typed or guessed.
- **Enforced by:** `docs/IDENTITY.md`; `agent.token_hash` (e0a010e); `IdentityByToken`,
  `RequireAgent` (f578f15); `TestIntegrationTwoAgentsTwoTokensNoHints` through the real
  transport; installer one-join-per-client (11782d0).

### 1.2 `project_key` (the missed collision)
- **What happened:** Claude Code (started in the parent folder, above the git root) sent
  `project_key=taqueria_tracker`; Codex (in the git root) sent `taqueria`. Same repo, same
  remote. Two projects were created; both claimed `app/rest.go` at overlapping times
  (02:33:04–02:34:30 and 02:33:26–02:36:51) and no conflict fired, because claims are
  compared within one project only.
- **Why:** `project_key` is free text, created on first use, and nothing (tool schema,
  server instructions, skill) said how to choose it.
- **Rule:** a project is identified by the repository (normalized git remote URL); the key
  is a label. Paths are relative to the git root. Creating a project while the team already
  has others says so.
- **Enforced by:** **open** — fix in progress in `app/mcp/sessions.go` (repo URL matching,
  `repourl.go`) with a same-repo-different-keys collision test.

### 1.3 Duplicate teams
- **What happened (found, not yet hit):** `create_team` dedupes only by idempotency key
  (the team uuid derives from it). Same name + different key → a second team with a
  `-xxxxxx` slug. Only `install.sh` checks `list_teams` by name first.
- **Rule:** the server refuses a same-named team on the caller's account unless explicitly
  asked; agents call `list_teams` before `create_team`.
- **Enforced by:** **open** — planned in `docs/CLI.md` §4.

### General rule
Any identity value — agent, project, team, session — comes from **the credential**, **the
repository**, or **a file a tool wrote** (`~/.metiche/env`, `.metiche`). Never from a
model's guess. When one looks free-text in a tool schema, that is a bug.

## 2. Only `Authorization` reliably reaches the server

- **Claude Code drops custom headers from a plugin's `.mcp.json`.** Proven by the server's
  "which headers arrived" log: only `Authorization` arrived; `X-Metiche-Client-Key` never
  did. → The plugin is skill-only (0.2.0); the server is registered by `claude mcp add` with
  a literal per-agent bearer.
- **Codex launched from the GUI has no shell environment**, so `bearer_token_env_var`
  fails (`failed (0 tools)`, real reason only in Codex's SQLite log). → The installer writes
  literal `http_headers = { Authorization = "Bearer …" }`.
- **`Mcp-Session-Id` is transport state, never identity.** The go-sdk builds the session
  context from `initialize`; auth must be re-read on every call from `req.Extra.Header`.
  → `authTool` in `app/mcp/safetool.go`.
- **Plugins are cached by version.** `claude plugin update` said "already latest" and
  shipped nothing. → Bump `plugin.json` **and** `marketplace.json` together (they had
  drifted: 0.1.1 vs 0.1.0).
- **Rule:** identity rides on the one header every MCP client forwards. Any second channel
  is presumed lost until the server log proves it arrives.

## 3. Verify through the artifact you produced, not around it

- **Installer:** it proved "the token works" with its own curl. That caught nothing,
  because every failure was in what each *client* did with the file. → Proof is: read the
  config the installer wrote, extract URL + bearer, make a real call with only that; where a
  client CLI can probe its own config (`claude mcp get`), use it.
- **Mobile screenshots:** headless Chrome `--window-size` screenshots showed clipping that
  wasn't there. → Measure with DevTools device emulation
  (`Emulation.setDeviceMetricsOverride`); prod re-measured at 0 clipped elements.
- **Tests that can't fail prove nothing.** → Mutation runs: break the code on purpose, show
  the test fail, restore, show it pass. Required for every key check (e.g. 74752ea's
  installer fix reproduces the owner's exact error when reverted).
- **A stale server answers too.** Testing against an old binary still on `:8080` looked
  like a pass. → Build to an explicit binary path; confirm the listener with `lsof`.
- **Prod state is checked from outside**: served `install.sh` hash vs the commit, tool
  count, CRUD probes, DB counts — not the deploy log.
- **MySQL's `RowsAffected` counts changed rows, not matched rows (board login).**
  - **What happened:** the sign-in link's single-use guard is `UPDATE … SET consumed_at = now
    WHERE … AND consumed_at IS NULL`, and `RowsAffected == 1` or refuse. A reuse replayed in the
    same second writes an identical `consumed_at`, changes nothing, affects 0 rows and is refused
    **even with `consumed_at IS NULL` deleted**. So a same-second reuse test cannot fail, and the
    mutation check would pass against broken code. Timestamps are `DATETIME(0)`.
  - **Rule:** a test of an atomic check-and-spend replays at least 1 s later, or backdates the
    spent column first (`browser_mysql_test.go` backdates `consumed_at` by a minute).
    `docs/BOARD_LOGIN.md` §8 verification 5 says the same for the smoke.

## 4. Installer and the user's machine

- **Our own profile line fools us.** The installer adds a line to `~/.zshrc` that loads
  `~/.metiche/env`, so `METICHE_TOKEN` is set in every shell. After the prod wipe, that dead
  token looked like a token *passed on purpose* and the installer refused ("refusing to
  configure anything with a token that does not authenticate") instead of starting a new
  identity. → A `$METICHE_TOKEN` byte-identical to the saved one is the saved token.
  Enforced by 74752ea (`anchor_token`, `TOKEN_FROM_PROFILE` / `TOKEN_EXPLICIT`).
- **Same-shell re-run gap — open.** Right after an install creates a new identity, the
  current shell still exports the old token, which no longer matches the file → a re-run in
  that shell is treated as explicit and refused. A new terminal is fine.
- **Never overwrite a user file without reading it first.** `~/.codex/AGENTS.md` (2.8 KB of
  the owner's content) was overwritten because a `grep -c … || …` read "zero matches" as "no
  file". Recovered byte-exact from a Codex session log. → The installer only edits a
  delimited `<!-- metiche:start -->…<!-- metiche:end -->` block, backs up every file it
  changes as `<file>.metiche-backup-<timestamp>`, and has `--dry-run`.
- **Shell traps in harnesses:**
  - `grep -c` exits 1 on zero matches; `||` after it runs the "missing" branch.
  - zsh does not word-split `$VAR` (an H verification applied an empty patch). Use explicit
    args or `set --`.
  - `ZDOTDIR` leaked into test runs. Use `env -i` with scratch `HOME`, `CODEX_HOME`,
    `ZDOTDIR`; never the real home.
- **A dead token and a failed check are different.** 401 with health OK → new identity,
  announced. Network error, 5xx, 401 with the DB down → refuse, write nothing.
- **Legacy state converges, it isn't left behind:** `metiche-direct`, the old Codex table,
  `METICHE_CLIENT_KEY` are removed with backups (11782d0).

## 5. Privacy and security

- **Generated CRUD was publicly reachable for ~4 hours.** nuzur's generated REST routes
  (accounts with token hashes, invites with join codes, writes) were mounted under the
  public ingress. Audit found no misuse; reads can't be ruled out. → Emergency ingress
  patch, then default-deny in code and in the charts.
  Enforced by 48da6e1: `DenyUnlisted` + `AllowedRoutes` in `app/rest.go`,
  `rest_deny_test.go`, per-host ingress `paths` allowlists with a chart guard that refuses
  `/` Prefix.
- **Rule:** a new route is unreachable until it is added to the allowlist in code *and* the
  chart. Generated surface is never public by default.
- **Boards leaked to anyone.** A demo team appeared in private tabs and on the owner's
  phone. → Only demo teams are listed publicly; private teams 404 (indistinguishable from
  nonexistent); `/healthz` counts only live teams (c36994c).
- **Consequence, open:** there is no viewer login, so the only way to see a private board is
  to make the team public. Board login (a one-time link from the terminal) is planned in
  `docs/BOARD_LOGIN.md`. Until then, don't print a board URL for a private team — it's a 404.
- **Secrets:** the repo is public. Never print or commit tokens, join codes, passwords or
  DSNs — not in docs, logs, test fixtures, reports, or `claude mcp add` output shown to a
  user. Snapshot redaction keeps tokens out of `team_event`.
- **Prod data wipe** on request: backups taken first
  (`/root/metiche-backups/…`), never a destructive step without one.

## 6. Deploy and operations

- **Helm `--reuse-values` turned a numeric image tag into a float** → `InvalidImageName`.
  → Always `--set-string` for tags, an `imageTag` helper in the charts, never
  `--reuse-values` (48da6e1, `helm-deploy.sh`).
- **Images are built from `git archive <commit>`, never the working tree** — the tree often
  holds another agent's uncommitted work.
- **The box has no image builder.** No docker, buildah or nerdctl there: images are built
  on the Mac with `docker buildx build --platform linux/amd64`, then
  `docker save | ssh … 'microk8s ctr image import -'`. Helm is `microk8s helm3` (no `helm`
  on PATH). Before an upgrade, render the new chart with the live values and diff it against
  the running manifest.
- **`api.metiche.xyz/healthz` is a 404 by design** — that host only routes
  `/v1/metrics/mcp`. Check health at `metiche.xyz/healthz` and via MCP.
- **Migrations before binaries.** `agent.token_hash` ALTER shipped before the backend that
  reads it: old binary on new schema is fine; new binary on old schema breaks every join.
  `apply-schema.sh` is `CREATE TABLE IF NOT EXISTS` only → dated ALTER files in
  `deploy/sql/` (`2026-09-agent-token-hash.sql`), verified with `SHOW COLUMNS` first.
- **MySQL JSON columns:** passing `[]byte` fails (MySQL 3144 with `interpolateParams`) →
  pass `string(...)`; every DSN, including tests, uses `interpolateParams=true`.
- **MySQL chart** needs `runAsUser: 999`.
- **nuzur Dockerfile ENTRYPOINT** names the identifier, not the module basename → the chart
  sets `command: ["/root/backend"]`. Real fix is upstream — **open**.
- **Rate limiter is effectively global — open.** It keys on the client IP, but without
  trusted-proxy handling (`METICHE_TRUST_PROXY`) every request comes from the ingress pod
  IP. `create_team` is 5/hour for everyone combined; retries burn it.
- **`build-images.sh` doesn't run on either machine — open.** Rollouts follow the previous
  rollout's steps instead.
- **Permission checks:** the Claude Code auto-mode classifier blocks remote writes and
  production deploys. Don't route around it — ask the owner, who approves in chat or adds
  a rule.

## 7. Databases in pods and the nuzur agent

- **A database in a pod still needs a password.** MySQL listens on the cluster network;
  any pod can reach it unless a NetworkPolicy says otherwise, and anything outside the pod
  (a host service, another pod) is a network client. Socket auth only works for a process
  sharing the container's socket and doesn't cross the container boundary cleanly. → A
  dedicated read-only user (`nuzur_ro`) with a generated password kept in a Kubernetes
  secret; nobody types it.
- **The nuzur agent can run as a pod**, and that is the chosen setup (`docs/NUZUR_AGENT.md`,
  being reworked). What must be right:
  - **Persist the config directory** (pairing uuid + token, connection registry, encrypted
    DSN) on a PVC. Without it, a pod restart forgets the pairing and re-pairing creates a
    new agent — the one thing the owner asked to avoid.
  - **Stable identity for the keyring.** nuzur-cli's file-keyring passphrase is sha256 of
    hostname + `/etc/machine-id` + `$USER` (`agent/connections/keyring.go`). A Deployment's
    hostname changes every restart → the DSN no longer decrypts. → StatefulSet (stable
    hostname), a fixed machine-id file from the chart, `USER` set explicitly, and a startup
    check that refuses to run if any changed.
  - **`NUZUR_AGENT_DSN` is not a shortcut.** On `agent start` it is a legacy fallback for
    machines with no registered connections, not tied to a published connection.
  - **Pair once, by hand.** `agent pair` with a one-time token (15 min) from
    `app.nuzur.com/pair`; `agent connection add --uuid <recorded>`; after that `agent start`
    only reconnects. Never `nuzur-cli connect`, `agent install`, `pair --force`, or a login
    on the box — each can mint a new agent or connection.
  - **Identify agents by uuid, never by name.** nuzur-cli can't set an agent name (it's the
    hostname), so two agents named `localhost` exist; one serves another project and is
    never touched.
- **Data exposure:** views keep every column name and return NULL for secrets (the data
  manager uses `SELECT *`, so column GRANTs would break it); an allowlist policy marks every
  column `expose` or `redact`, and a new column stops the generator.
- **Reference point:** nuzur's own `deploy` runs the agent as a host systemd service and
  passes the DSN in argv during bootstrap — the pod setup is new ground.

## 8. How the work is run

- **Orchestrate, and demand pasted proof.** Agents report files written, exact commands and
  real output. "Tests pass" with no output is treated as untested. The orchestrator re-runs
  the key proof before committing.
- **Explicit file ownership per agent.** `auth.go` was clobbered when two agents edited it
  at once. Every brief names the files an agent owns; two agents never share one.
- **nuzur schema first, owner approval before codegen.** Generated `DO NOT EDIT` files are
  never hand-edited; hand-written code lives in `app/`.
- **Commits are authored by the owner**, with no co-author or session trailers.
- **Forbidden strings and secrets are grepped** in every changed file before commit and push.
- **When a demo breaks, fix the structure, not the symptom.** The night's header-of-the-hour
  fix added a second identity channel that failed the same way; the durable fix removed the
  need for it.
- **A mutation check that never mutated anything (board login).**
  - **What happened:** the orchestrator's mutation check ran after a `cd` that failed. The
    backup step never happened, the mutation was committed, and the tests "passed" because,
    without `METICHE_TEST_MYSQL_DSN`, they were skipped. It was caught before push and the commit
    was amended.
  - **Why:** each step assumed the one before it had worked. A skipped test prints `ok`.
  - **Rule:** use absolute paths, not `cd`. Check the backup exists before mutating. Treat a
    skipped test as **not run**: paste `-v` output that shows the test ran and failed under the
    mutation.
- **API spend limits killed parallel agents mid-task, twice (board login).**
  - **What happened:** agents stopped partway through their files. The work on disk survived, and
    resuming the same agents finished it.
  - **Rule:** work in small steps, and leave every file consistent (compiling, tests runnable) at
    the end of each step, so an agent stopped at any point can be resumed or its files handed on.
